## 1. 背景与目标

**背景**：1号员工（Digital AI Employee 1#）已有对外官网（spec-ai.cn）与桌面 App、物理硬件接入体系。目前缺乏一个**管理者视角**的统一监控入口——管理者无法实时了解：多少 App 在线、多少硬件接入、token 消耗了多少、哪些用户付费、有没有设备异常。

**目标**：搭建 SPEC 品牌第二站——**接入管理看板**（Admin Dashboard），私有部署，实时汇聚 App/硬件遥测与付费数据，为运营决策提供数据支撑。

**核心价值**：
- 实时掌握 App/硬件接入全景（在线、离线、地域、版本）
- 量化资源消耗（token 用量、按 provider 分布）
- 付费情况一目了然（订阅状态、到期、对账差异）
- 异常主动通知，无需人工盯屏
- 历史趋势与报表支撑扩容/定价/运营决策

**AI-Native 定位**：本看板不是"给人看的报表"，而是**一个 AI 运营助手的感知层**——系统自己发现问题、解释问题、给出动作建议，管理者只做决策。遥测直报 + 全量长留的架构天然是 AI 分析的良好底子（详见 §4.9）。

## 3. 核心场景

1. **看大盘**：打开看板，秒级看到在线 App 数、在线硬件数、今日 token 用量、付费用户数/金额、异常数。
2. **查明细**：下钻到设备/用户明细（在线状态、最后心跳、版本、地域、订阅状态、今日 token）。
3. **收告警**：设备掉线、token 异常消耗、付费异常（对账差异）时，经钉钉/Telegram/邮件通知。
4. **看趋势**：查看 token 用量、在线峰值、付费转化、设备增长的历史曲线。
5. **导出报表**：按日/周/月导出 CSV 报表，用于运营复盘。
6. **对账**：App 上报的订阅状态与 Cloudflare 账号体系的订阅记录定期核对，标记差异。
7. **AI 问答（一期）**：用自然语言问看板数据（"为什么今天 token 用量翻倍？""哪些设备掉线了？"），AI 自动转查询并回图表/结论。
8. **AI 日报（二期）**：每日自动生成自然语言运营摘要（在线峰值、token 成本、异常、环比）。

## 4. 功能需求（FR）

### 4.1 遥测上报协议（App / 硬件 → 私有服务器）

**两端均未实现上报，需从零定义统一协议并输出对接文档**（App 端由产品端开发、硬件端由第三方按协议接入）。

- **设备注册**：App/硬件首次接入时注册（设备标识、类型、版本、所属用户），获得/绑定设备凭证。
- **心跳**：周期上报在线状态（建议默认 30s 一次；>90s 未上报判定离线，阈值可配）。
- **事件**：连接/断开、任务执行、硬件状态变化等事件上报。
- **token 用量**：上报用量明细（provider、模型、输入/输出 token、费用估算），按设备/用户聚合。
- **订阅状态**：心跳携带用户订阅状态（plan、到期时间），用于付费看板与对账。
- **协议要求**：HTTPS + JSON；鉴权用设备凭证（token/签名）；字段可扩展（版本化）；容错（上报失败重试、不阻塞业务）。

### 4.2 实时监控大盘

- **实时性**：关键指标（在线数、token 用量、付费状态、异常）秒级更新（WebSocket 推送）；明细/报表级数据可分钟级。
- **指标区**：
  - App 在线 / 硬件在线（总数、离线数）
  - 今日 / 实时 token 用量（含按 provider 分布）
  - 付费用户数、付费金额、订阅到期预警
  - 异常事件数（掉线、异常调用、对账差异）
- **明细区**：设备/用户列表（状态、最后心跳、版本、地域、订阅、token），支持筛选与排序。
- **下钻**：点击设备/用户查看详情（历史事件、token 曲线、订阅轨迹）。

### 4.3 异常告警

- **告警类型**（初始集，规则阈值可配）：
  - 设备离线超时（连续 N 个心跳周期未上报）
  - token 异常消耗（单设备/单日超过阈值，或激增）
  - 付费对账差异（App 上报与 Cloudflare 记录不一致）
  - 注册/上报异常（凭证无效、频率异常）
- **渠道**：钉钉群机器人、Telegram Bot、邮件（三选一或多选；渠道凭据配置化）。
- **行为**：告警去重、静默期（防轰炸）、状态（触发/恢复）。

### 4.4 历史趋势分析

- 趋势曲线：token 用量（按天/按 provider）、在线峰值、设备增长、付费转化、告警统计。
- 时间范围：7 天 / 30 天 / 90 天 / 自定义。
- 数据基于聚合存储（原始数据全量保留，见 NFR-5）。

### 4.5 报表导出

- 支持按日/周/月导出：设备接入报表、token 用量报表、付费报表、告警报表。
- 格式：CSV（首版）；后续可加图表化 PDF（不做承诺）。

### 4.6 付费对账（上报 + 同步）

- **App 上报**：心跳携带订阅状态（用户/设备维度）。
- **Cloudflare 同步**：定期从第一站账号体系（users/orders/subscriptions）拉取权威订阅数据（只读）。
- **对账**：比对两端，标记差异（App 上报 Pro 但服务端记录 free、到期时间不一致等），差异进告警。
- **口径**：Cloudflare 为付费权威来源，App 上报作实时辅助。

### 4.7 管理员账号

- 单管理员：用户名 + 强密码 + **TOTP 双因素**（可配置是否强制）。
- 会话：服务端会话/JWT，超时与失效机制；登录失败限流。
- 密码存储遵循品牌后端标准（PBKDF2/argon2 高迭代）。

### 4.8 国际化

- **中 / 英双语**，右上角切换按钮（交互复用第一站：localStorage 记忆 + 切换即生效）。
- 管理端默认中文，切英文后全站文案切换（含表格、图表、告警文案）。

### 4.9 AI-Native 能力（按优先级分期）

> 定位：AI 运营助手。优先级 P0 一期必须、P1 二期、P2 后期；L1 字段预留是"现在不做、以后要改协议"的坑，**P0 必须现在就做**。

#### P0 · 一期（必须）

- **4.9.1 遥测协议预留 AI 友好字段**
  - 事件除结构化字段外预留 `event_desc`（自然语言事件描述，如"蓝牙连接断开，重试 3 次"）——未来问题聚类、相似案例分析直接可用，无需重新埋点。
  - 必报维度：App 版本、硬件型号、地域、网络类型（AI 归因的基本维度）。
  - 原始事件全量长留（已在 NFR-5），供 AI 分析直接取用，不只在聚合表上算。
- **4.9.2 会话式数据查询（NL → 数据）**
  - 看板内嵌 AI 对话框：管理者自然语言提问（"为什么今天 token 用量翻倍？""哪个用户调用异常？""近 7 天哪个版本掉线率最高？"）。
  - 系统将问题转为受控查询（白名单表/字段 + 只读权限 + 查询超时），返回图表/结论，支持追问。
  - 查询隔离：AI 只能访问管理员可见的数据范围；不得执行任意 SQL（结构化转译）。
  - LLM 接入：可插拔（见 §10 待决策-LLM API）；私有数据出域需策略（见 §9 假设）。

#### P1 · 二期

- **4.9.3 自适应异常检测**：按设备类型/地域/时段学习正常基线，偏离基线才告警——替代固定阈值（减少误报、捕获慢异常）。
- **4.9.4 自动运营日报**：每日固定时间生成自然语言摘要（在线峰值、token 成本、环比、异常事件、对账差异），推送到告警渠道。
- **4.9.5 告警相关聚类与处置建议**：将散点告警按相关性聚类成"事件故事"（如"token 激增 + 某版本掉线率上升 + 付费到期"同源）；AI 标注严重级别并给出初步处置建议（如"疑似 v1.1.3 回归，建议回滚"），管理者一键采纳/忽略。

#### P2 · 后期

- **4.9.6 容量预测**：按 token 消耗速率预测扩容/配额升级时机。
- **4.9.7 流失预警**：使用量持续下滑 + 订阅临近到期 → 提前标记高风险用户。
- **4.9.8 成本优化建议**：检测某用户/某 provider token 异常高时，建议切换模型或限流。

## 5. 非功能需求（NFR）

1. **实时性**：大盘关键指标秒级；心跳/事件从上报到可见 ≤ 3s。
2. **可扩展演进**：初期支撑小规模（千台内）；数据模型、采集与存储设计必须可平滑升级到中等（数千台）/大规模（万级+）——原始+聚合分层、采集与展示解耦、部署可横向加实例。
3. **可移植性**：全栈容器化（Docker Compose），先在阿里云海外（免备案）运行，后续**一键迁移到本地私有服务器**，无云厂商绑定。
4. **安全**：公网访问 + 管理员鉴权 + TOTP；上报接口凭证鉴权；传输 HTTPS；管理界面可配 IP 白名单。
5. **数据保留**：原始遥测事件与聚合数据**全部长期保留**（用户已确认）；存储按时间分区便于归档/清理策略预留。
6. **可靠性**：上报接口高可用（失败不丢业务、可重试）；告警不因单点失败丢失；服务自恢复。
7. **品牌一致性**：前端完全遵循 `BRAND-DESIGN-SPEC.md`（D+B 深色体系、组件、动效、taste-skill 审查），发布前过全套验证门禁。

## 6. 技术设计要点（架构方向）

> 本节为设计倾向，供技术方案阶段细化；详细 schema/接口/文件结构在规划阶段确定。

### 6.1 总体架构

```
App / 硬件端 ──HTTPS/JSON──▶ /ingest（采集 API，设备凭证鉴权）
                                    │
Cloudflare 账号体系 ──定期拉取──▶ 对账任务
                                    ▼
                        存储层（Postgres：原始事件表 + 聚合表，时间分区）
                                    │
   ┌────────────┬────────────┬─────┴─────┐
   ▼            ▼            ▼           ▼
 看板 API       WebSocket   告警引擎     报表导出
（REST+WS）   （实时推送） （钉钉/Telegram/邮件）
   │             
   ▼
 管理端前端（D+B 深色，中英切换）
```

### 6.2 选型倾向

| 层 | 倾向 | 理由 |
|---|---|---|
| 后端 | Node.js（与品牌后端技术栈一致） | 团队熟悉、零额外学习成本 |
| 存储 | **Postgres**（原始事件 + 聚合表，时间分区） | 全量长留、SQL 灵活、可平滑升级；后续可加 TimescaleDB 插件应对大规模时序 |
| 实时推送 | WebSocket（服务端 → 看板） | 秒级刷新 |
| 采集 | 独立 `/ingest` 接口 + 落库（与展示解耦） | 采集压力不影响看板查询 |
| 部署 | **Docker Compose**（app / db / 可选 nginx） | 阿里云 ↔ 私有服务器零成本迁移 |
| 告警 | 内置引擎 + 各渠道 webhook | 钉钉/Telegram 走 webhook，邮件走 SMTP |

### 6.3 数据保留
- 原始事件表 + 聚合表均长期保留；聚合表为大盘/趋势/报表的主数据源。
- 时间分区（按月），预留归档/清理策略（当前不启用）。

### 6.4 部署与迁移
- **阶段一**：阿里云海外区域 ECS（免备案），域名 DNS 走 Cloudflare（隐藏服务器 IP + 自动 HTTPS），Docker Compose 一键启动。
- **阶段二**：本地私有服务器就绪后，同 Compose 配置迁移（导出数据 → 导入 → 切 DNS），无云厂商绑定。
- 待采购项：阿里云 ECS（海外）、新域名（用户自选）、SMTP/钉钉/Telegram 凭据。

### 6.5 前端
- 按 `BRAND-DESIGN-SPEC.md`：设计令牌、组件、粒子背景（可选弱化）、动效、taste-skill 审查。
- 中英双语切换：复用第一站交互模式（切换按钮 + localStorage + data-i18n 机制，管理端字典为 zh/en 两套）。
- 图表组件：趋势曲线、大盘数字卡、设备列表；图表样式符合深色体系。

### 6.6 AI 分析层（可插拔，随 P0-P2 渐进）

- **架构**：独立分析服务（与采集/展示解耦），通过受控接口访问聚合与原始数据；LLM 接入可插拔（provider/模型配置化）。
- **LLM 选型（已决策）**：默认 **DeepSeek API**；备用 **SPEC 本地开源专用模型**（私有服务器自托管推理，如 Ollama/vLLM 服务）。设计为多 provider 可插拔 + 自动降级：DeepSeek 不可用/出域受限时自动切换本地模型；敏感查询优先走本地模型（数据不出域）。
- **安全边界**：
  - 会话式查询 = **结构化转译**（NL → 受控查询 DSL → 只读执行），禁止任意 SQL 透传；查询超时 + 结果量上限。
  - 私有数据出域策略：LLM 调用前明确哪些字段允许出域（匿名化/聚合后出域），敏感字段（用户邮箱、设备标识）默认脱敏。
- **数据供给**：P0 起保留 `event_desc` 与原始事件全量（供 AI 追因），聚合表供快速查询。
- **产物**：AI 生成的图表/摘要/建议在管理端以"AI 面板"呈现，与固定报表并列；所有 AI 结论可溯源（附数据依据）。

## 7. 范围边界

**包含（本期 = 一期）**：
- 遥测上报协议定义 + `/ingest` 采集实现 + 对接文档（输出给 App/硬件端）
- 管理看板（大盘/明细/趋势/报表/告警/对账/账号）
- **AI P0**：协议 AI 友好字段（`event_desc`/版本/环境）+ 会话式数据查询
- 部署方案（阿里云海外 → 私有服务器迁移）

**明确不做（本期）**：
- 不替换/不修改现有 Cloudflare 账号体系（只读对账）
- 不开发 App/硬件端 SDK（只交付协议规范，两端各自实现）
- 不改造第一站官网
- 不实现多角色 RBAC、多管理员（单管理员起步）
- 不承诺图表化 PDF 报表（CSV 起步）
- **AI P1/P2 不做进一期**（自适应检测/日报/告警聚类=二期；预测/流失/成本建议=后期）——但数据模型与架构必须为其预留（P0 字段、原始事件长留、AI 层可插拔）

## 8. 成功标准

1. App/硬件端按协议上报后，管理者**秒级**看到在线数与接入明细。
2. token 用量按 provider 与设备/用户维度可查、可导、可看趋势。
3. 付费状态实时可见，且与 Cloudflare 对账**无静默差异**（差异必告警）。
4. 设备掉线/异常 token/对账差异**按时送达**钉钉/Telegram/邮件。
5. 全栈 Docker Compose 一键部署，**阿里云 ↔ 私有服务器迁移演练通过**。
6. 前端通过 `BRAND-DESIGN-SPEC.md` 全套验证（含 taste-skill 审查与测试门禁）。
7. 中英切换全站无漏译。
8. **AI（一期）**：会话式查询可正确回答常见运营问题（"今日 token 用量""掉线设备"等），且仅访问管理员可见数据、无任意 SQL 风险。
9. **AI（二期/后期）**：自适应检测误报率明显低于固定阈值；日报/告警聚类产出可直接使用。

## 9. 依赖与假设

- **新域名**：用户自行注册（待定具体域名），DNS 托管 Cloudflare。
- **阿里云**：用户已有账号；需开通海外区域 ECS（规格待评估）。
- **凭据**：SMTP（告警邮件）、钉钉群机器人 webhook、Telegram Bot token——用户提供。
- **端侧开发**：App 端（产品端仓库）与硬件端（第三方）按协议文档实现上报——排期待用户协调。
- **Cloudflare 对账**：第一站账号体系需提供只读拉取渠道（现有 API/D1 导出），权限由用户开通。
- **token 口径**：由 App 端上报，provider 维度由 App 定义——字段以协议文档为准。
- **LLM API（AI 功能，已决策）**：默认 DeepSeek API（密钥用户提供）；备用 SPEC 本地开源模型（私有服务器自托管，数据不出域）；敏感查询优先本地模型。
